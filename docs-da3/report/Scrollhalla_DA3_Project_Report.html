1.1 Unit testing

Unit tests pin the business rules that the rest of the system depends on: the default values of a Task, the MoSCoW weight table, the exact Smart Backlog scoring formula, the severity classification and risk thresholds of the Sprint Risk service, and the normalisation each parser performs. The RSS client is replaced by a shared stub so no test touches the network.

1.2 Integration testing

The integration suite drives the real application over HTTP with supertest. The composition root in routes/api.ts is left untouched, so the test also verifies that dependency injection wires the controllers correctly — for instance, that a task created through /api/tasks is visible to the Smart Backlog and Team controllers, which share the same TaskController instance. Five integration scenarios are covered:

  • Task CRUD flow — create, read (view counter increments), update, comment, delete, and 404 on every verb afterwards.
  • Cross-controller — a high-engagement task rises to the top of /api/smart-backlog; reassignment changes team workload.
  • Feed pipeline — cold cache triggers on-demand harvest through Factory → Parser → Cache; the second request is a REDIS_CACHE_HIT; one failing publisher does not break the timeline.
  • Sprint risk — the endpoint degrades to the resilience fallback when the status feed is offline.
  • Auth flow — register → duplicate refused → login → protected profile with bcrypt and JWT; identical 401 for wrong password and unknown user.

1.3 Regression testing

The regression pack protects behaviour that users and the frontend already rely on. REG-01 snapshots the status code and the shape of every endpoint's response — volatile values such as IDs and timestamps are reduced to their type so the snapshot only changes when the contract changes. REG-02 is a golden master of the seeded backlog ranking. REG-03 pins edge cases: the documented storyPoints: 0 → 3 coercion, the 100% cap on team utilisation, non-enumerating login errors, and malformed JSON being handled by the global error handler.

Listing 2 — Contract snapshot that ignores volatile values (backend/tests/regression/api-contract.reg.test.ts)

/** Replace volatile values (ids, timestamps, latencies) with their type so snapshots are stable. */
const shape = (v: any): any => {
  if (Array.isArray(v)) return v.length ? [shape(v[0])] : [];
  if (v && typeof v === 'object') return Object.fromEntries(Object.keys(v).sort().map(k => [k, shape(v[k])]));
  return typeof v;
};

1.5 Mutation testing

Line coverage only shows that code ran; it does not show that a test would fail if the code were wrong. Stryker answers that question by generating mutants — >= turned into >, || into &&, a string emptied, a branch forced to true — and re-running the suite against each one. A mutant that no test notices survives and marks a weak spot.

The baseline run surfaced four real problems, each fixed in a separate commit:

5 in authMiddlewareTests checked status codes but never the response body, so emptying the error message went unnoticed.Assert full 401 and 403 bodies.

Remaining survivors are equivalent mutants, meaning changes that cannot alter observable behaviour, so no test can kill them. Examples: status || TaskStatus.TO_DO in the controller (the Task constructor applies the same default); item.pubDate || new Date() (items without a date are already filtered out above); the unused parserName field; and log-message strings. They are documented here rather than suppressed.

2. Version Management and System Building

2.1 Branching strategy

The project follows GitHub Flow, as set up in DA1: main holds the stable, deployable version and every unit of work lives on a feature/* branch merged through a pull request. Each review has its own branch (feature/da2-design, feature/da3-testing) next to the functional branches (feature/onboarding-rss-enhancements, feature/opml-feed-exporter). Commits use the Conventional Commits prefixes feat, fix, test, refactor, docs and ci, so the history reads as a changelog. Releases are marked with semantic-version tags.

2.2 System building

The system is built at three levels, and each one is reproducible from a clean checkout:

  1. Component builds. The backend runs npm run build, which is prisma generate followed by tsc, the type-check gate. The frontend runs npm run build, which is a Vite production bundle of 215 kB (65 kB gzip).
  2. Container images. The backend uses a multi-stage Dockerfile, with a build stage and a slim runtime stage on node:20-alpine. The frontend Vite bundle is served by Nginx, which also reverse-proxies /api.
  3. System composition. docker compose up --build starts four services: postgres:15, redis:7, the backend and the frontend. They share one network, and health-checked dependencies control the start order.

2.3 Continuous integration

A GitHub Actions workflow (.github/workflows/ci.yml) runs on every push to main and feature/**, on every pull request and on every v* tag. It has four jobs:

  • backend builds the code, then runs the unit, integration and regression tests and coverage.
  • mutation runs Stryker after the backend job and fails the pipeline if the score falls below 60%.
  • frontend runs the Vitest tests and the production build in parallel with the backend job.
  • docker builds the whole compose stack once both the backend and frontend jobs pass.

The coverage report, the mutation report and the frontend dist/ are uploaded as artifacts.

6. Problem Statement

Readers face extreme algorithmic noise, cluttered interfaces and information overload in mainstream social media and news apps. Feeds are ranked by engagement rather than by the reader's intent, and long-form text is presented in high-contrast, ad-dense layouts that tire the eye. Standard RSS readers solve the control problem but keep a dated, list-heavy interface that discourages continuous reading.

Scrollhalla is a minimalist, mobile-first RSS/Atom aggregator that combines two things:

  • the control of RSS, so readers decide which sources they follow;
  • the frictionless discovery of a vertical, Reels-style scroll.

It presents articles in a calm e-reader aesthetic, with a warm paper background and serif reading text. Feeds are harvested in the background and cached, so opening the app never waits on third-party servers.

Target users.

  • The Deep Thinker reads long-form essays, tech blogs and news, and wants a paper-like experience without eye strain.
  • The Curator is tired of algorithms choosing their feed and wants to subscribe explicitly through tags and lists.

Success criteria.

  • Feed loads under 500 ms. Measured at 0–2 ms from the Redis cache.
  • Standard RSS 2.0 and Atom 1.0 feeds parse correctly. Verified by the parser unit tests.
  • The system deploys with a single command through Docker Compose.

8. System Architecture and System Design

8.1 Architectural style

Scrollhalla is a layered (n-tier) architecture. It runs as four containers orchestrated by Docker Compose: an Nginx-served React SPA, an Express API, PostgreSQL and Redis. A layered style was chosen over microservices because the deciding constraint is team size, not scale. Two developers would pay the full coordination cost of independent services and gain nothing, since there is no independent scaling requirement.

One refinement is deliberate: the read path is inverted. A cron worker harvests the external feeds every 15 minutes and writes a normalised timeline to Redis, so GET /api/feed becomes a single key lookup. Freshness is traded for latency and for isolation from third-party servers.

8.2 Design principles and patterns

  • Abstraction and polymorphism. The abstract BaseParser defines one contract, parse(url): IFeedItem[]. RssParser and AtomParser implement it.
  • Factory Method. FeedParserFactory keeps object creation out of the callers. DA3's mutation testing simplified it to a single Atom check (§1.5).
  • Rich domain model. Task.getDaysInBacklog() and BacklogItem.getMoscowWeight() keep behaviour next to the data it uses.
  • Strategy and configuration. SmartBacklogService takes injectable weights, which the tests exercise directly.
  • Dependency injection. routes/api.ts is the composition root, and a single TaskController is shared by the Backlog and Team controllers.
  • Resilience. CacheService falls back to an in-memory store, and SprintRiskService falls back to known telemetry.

9. Design of Tests

9.1 Strategy

The test design follows the architecture's layers. Each level replaces exactly one boundary, which is why every failure points to a single place:

  • Unit tests isolate a class from all I/O.
  • Integration tests keep everything real except the Layer-5 adapters: Prisma, Redis and outbound HTTP are swapped for in-memory fakes with the same interface.
  • Regression tests freeze the externally visible contract.
  • Mutation testing then measures whether the three levels above would catch a real defect.

9.2 Test-design techniques

  • Equivalence partitioning. MoSCoW priorities (4 valid plus 1 unknown); feed URLs (Atom, RSS, generic); auth headers (missing, wrong scheme, forged, expired, valid).
  • Boundary-value analysis. Risk thresholds at 19/20, 39/40 and 69/70 and the cap at 100; the risk floor of 5%; the 7-day incident window, exactly at the limit and one second over; getDaysInBacklog never below 1; team utilisation capped at 100%.
  • Decision tables. Severity classification from title and body keywords (Table 9.3, TC-U-SR).
  • State-based testing. The task lifecycle: create → read (views +1) → update → comment → delete → 404 on every verb.
  • Error guessing and fault injection. Network failure for each parser and the risk service; one failing publisher among several; Redis unavailable; malformed JSON body.
  • Golden master and contract snapshots. Used for the regression pack.

Appendix A — Software Requirements Specification

This SRS specifies Scrollhalla, a web-based RSS/Atom e-reader with a Reels-style reading feed. It is delivered as a React SPA and a REST API, deployed with Docker Compose. Listing E1 — Factory Method after the mutation-driven refactor (backend/src/parsers/FeedParserFactory.ts)

export class FeedParserFactory {
  public static createParser(formatOrUrl: string = 'AUTO'): BaseParser {
    return FeedParserFactory.isAtom(formatOrUrl) ? new AtomParser() : new RssParser();
  }
  private static isAtom(formatOrUrl: string): boolean {
    return formatOrUrl.toUpperCase() === 'ATOM' || formatOrUrl.includes('.atom') || formatOrUrl.includes('/atom');
  }
}

Listing E2 — Smart Backlog scoring (backend/src/services/SmartBacklogService.ts)

public calculatePriorityScore(item: BacklogItem): number {
  const viewScore = item.views * this.config.weightViews;
  const commentScore = item.commentCount * this.config.weightComments;
  // Logarithmic decay/growth for time in backlog to avoid extreme skew
  const ageScore = Math.log(item.daysInBacklog + 1) * 10 * this.config.weightBacklogAge;
  const complexityScore = item.storyPoints * this.config.weightStoryPoints;
  const finalScore = (viewScore + commentScore + ageScore + complexityScore) * item.moscowWeight;
  item.priorityScore = Math.max(0, finalScore);
  return item.priorityScore;
}

Conclusion

Review 3 takes Scrollhalla from an untested codebase to one with a four-level automated test suite of 116 tests, 92% line coverage and a 96.5% mutation score, enforced by a CI pipeline that builds and tests every push. Mutation testing was the most informative of the levels. Besides measuring the suite, it found dead code in the parser factory and three blind spots that coverage figures had hidden. The system builds and runs end-to-end on PostgreSQL and Redis with live feeds. Twenty of twenty-three user stories are complete, and the remaining three are recorded with their current state.
